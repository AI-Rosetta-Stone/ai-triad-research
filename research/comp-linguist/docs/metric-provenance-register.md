## Why this register exists

Every scalar the system emits implies a measurement instrument. This register classifies each one so that false precision is a visible, countable property of the system rather than a critique waiting to be written.

New or changed metrics, judges, and verdict grammars run the six-check **instrument-integrity checklist** (`instrument-integrity-checklist.md`) before their output is cited as a disposition. **Truthfulness-vs-honesty limit:** behavioral honesty and consistency metrics (and RepE-style probes) measure whether a model asserts claims consistently with its own reasoning, not whether those claims match external ground truth; read them as honesty measures, not truth measures (arXiv 2607.14399 §3.1; 2310.01405).

**Classes:**

| Class | Meaning | Evidence requirement |
|---|---|---|
| `metadata` | Session identity/context. Not an instrument. | none |
| `observation` | Direct count or ratio of system events with no embedded judgment beyond what to count. | none |
| `echo` | Records the parameter value a debate ran under. The *parameter* it echoes is classified in the Parameters table. | none |
| `stipulated` | Instrument or parameter asserted by design. No evidence pointer exists. | none by definition |
| `derived` | Value or formula produced by analysis of data. | pointer to the analysis |
| `human-validated` | Checked against human judgment. | pointer to the study |
| `validated-negative` | Checked against human judgment and found NOT to measure what it claims. | pointer to the study |

**Rule (no grade inflation):** anything without an evidence pointer is `stipulated` by definition. New metrics and parameters must declare their class at PR time and be added here in the same PR (enforced via the CL review checklist).

**Rule (distribution-bounded validation, t/3342):** a classifier/judge GV-pass is bounded to its **validation distribution**. Never cite it as evidence for a *different* distribution without a fresh precision golden on that distribution. Origin: the fork-B contradiction classifier passed the same-doc/within-conflict golden (#1942) at 0.957 precision but scored **0.571** on the cross-conflict distribution (t/3339#9) — auto-merge OUT, census-merge (human dual-verify) only. The t/3339 cross-conflict golden was correctly required as a *separate* gate rather than inheriting the same-doc pass.

## Reporting-treatment (orthogonal tag)

A provenance class says how an instrument's *value* was established; a **reporting-treatment** tag says how a cited *number* was drawn — `single-draw` (one run / one labeling pass, no distribution) vs `n-draw distribution` (≥3 re-runs of the fixed config, reported as **mean±SD**, per instrument-integrity checks 4–5). The two are orthogonal: a `human-validated` scalar can still be a `single-draw`. Any headline cited as a **disposition** (not an indicative sample) must carry an `n-draw distribution` treatment; a `single-draw` headline is provisional (⚠). The tag distinguishes **estimation-uncertainty** (bootstrap CI of one draw) from **run-instability** (SD across n re-runs) — only the latter answers the arXiv 2607.14399 run-drift concern.

## Confidence quantities (five distinct instruments — do not pool)

The pipeline emits **five** confidence scalars that measure *different things*; pooling them (averaging, or gating one on another's threshold) is the category error the FIRE ≠ QBAF `base_strength` note already warns against (`claims-entity-fol-recommendations.md` §11 / R7.5). Each stays a distinct instrument measuring reliability/faithfulness at its own stage — **none is a truth measure**:

1. **`extraction_confidence`** — is this *claim* faithful to its source text? (extraction reliability, not argument quality).
2. **`fire_confidence`** — FIRE reliability of the claim's inferential structure (extraction-layer; the FIRE header makes the same not-argument-quality distinction). Threshold: `fire_confidence_threshold`.
3. **`retrieval_confidence`** — is the retrieved *taxonomy node* the right home for the claim/key_point? (`Invoke-RetrievalConfidencePass`; `RetrievalConfidenceThreshold` 0.45).
4. **`link_confidence`** — is this *surface string* really `ent-NNN` / `term:<cf>`? (entity/concept reference resolution). Method-dependent: **1.0** exact/alias; **cosine** embedding (concepts only, ≥ 0.55, `proposed`); self-report llm. Entity linking is precise-only (1.0). Effectiveness metric: `entity_link_precision` (pending, T5, on `Test-ExtractionQuality`).
5. **`formalization_confidence`** — is the `logical_form` a faithful FOL rendering of the claim? (formalization soundness; the prover is only as good as this — t/3126 / t/3127). Gates prover consumers.

A consumer needing an "overall trust" number must combine them **explicitly and named**, never silently — and must not substitute one stage's confidence for another's.

## 17. Calibration epochs: model changes behind debate defaults and tiers (t/3553, e/263)

**Rule (CL, SO-agreed e/263#5–#6):** any change to the model behind an `ai-models.json` `defaults[backend]` or `debateTiers.{tier}.{backend}` slot **starts a calibration epoch**. Calibration metrics (`crux_addressed_rate`, `convergence_score`, `repetition_rate` and the rest) are compared **within** an epoch, never across one. A cross-epoch shift is classified as a *model* change (class 4 of the `/cl-regression-diagnostic` 5-way classification), not a regression.

**Who writes the row:** nothing writes it automatically. The t/3553 refresh tool records an accepted proposal only as a flight-recorder `signoff` event, which is forensics, not this table (t/4032). So **every change to a `defaults` or `debateTiers` model, whether by accepted proposal or by hand edit, must add its row above in the same PR.**

**Checked, warn-only:** `npm run verify:config` reports every `defaults` or `debateTiers` slot whose **served model** changed since the merge-base with `origin/main`, when this table has no row with the same Slot and Old → new (t/4037, #2996; t/4041, #3000). It **warns and does not block.** Making it blocking needs TL Gate Verification and the mandatory Second Opinion.

**How to write the row:**
- **Registry id changed:** use bare ids, e.g. `claude-haiku-4-5 → claude-sonnet-5`. The `id:api` form is also accepted.
- **Same id, `apiModelId` repointed:** use `id:api` on both sides, e.g. `claude-haiku-4-5:claude-haiku-4-5-20251001 → claude-haiku-4-5:claude-haiku-4-5-20260301`. A bare `x → x` row doesn't satisfy it.

**Not the only safeguard:** calibration comparisons don't depend on this table. The machine split below keeps runs on different served models apart whether or not a row exists. This table is the human audit record.

### Machine split: the served-model fingerprint (t/4040, SO e/265)
Each calibration entry records what was actually served, captured **when the run starts** and never re-resolved later. The replication gate keys on these stored fields only.

| Field | Provenance class | Meaning |
|---|---|---|
| `model_pool` | instrument provenance (exact, not a judgment) | Multi-provider runs: `tier\|backend=registryId:apiModelId,…`, sorted, over the **eligible** backends only (those with a key and a tier entry). This is the population the per-run shuffle draws from, so permutations and subsets of it pool together, while a tier change, a repoint or an eligibility change splits it. |
| `model_api_id` | instrument provenance | Single-model runs: `registryId:apiModelId`. |
| `speaker_models` | forensics (not keyed) | The speaker-to-model assignment at init, for stratified analysis. **Not** in the gate key, because keying on the random assignment would fragment groups below n = 10. |
| `speaker_model_failovers` | forensics; presence is semantic | The last failover per speaker. **Presence excludes the run from the replication count.** The full history is in the FR `ai.fallback` events. |

**Statistical unit (CL decision, e/265#6/#8):** the eligible pool, not the realized assignment or the realized model set. With *e* eligible backends and 3 speakers, the realized set alone gives C(e,3) groups (56 for today's `basic` tier).

**One-time key-format boundary.** When #2998 lands, the gate key gains a 4th segment. Single-model groups gain `model_api_id`, so they **re-replicate once** (about 10 runs) before the gate can fire again. Legacy rows keep an empty 4th segment and form a model-mixed bucket that never pools with new rows. **A metric shift across this boundary is an instrument change, not a regression.**

**Coverage:** the engine path (CLI, headless, exploration) stamps the fingerprint from #2998. **Editor and web runs stamp it at session creation** from #3031 (`7680111e`, t/4044), using the same `computeModelFingerprint` and the **live** `ai-models.json`. They are created with `failover_tracking: 'unavailable'` and can earn `'tracked'` per turn from #3118 (below). **If the live registry hasn't loaded when the session is created, no fingerprint is stamped** (a WARN is logged): a stale bundled snapshot could name a model the backend no longer serves, and the key is frozen at creation. Such a row, and any pre-#3031 editor or web row, carries an empty 4th segment. **That is not an exclusion:** the empty-segment (legacy, model-mixed) group pools and counts toward n ≥ 10 like any other key. Editor and web rows that haven't earned `'tracked'` are kept out of the count by their explicit `failover_tracking: 'unavailable'` (below), not by the empty segment. *(Correction, t/4040#18: an earlier version of this paragraph said the empty segment "fails closed into model-mixed". The gate never read `failover_tracking` on unfingerprinted rows, so it didn't.)*

**Failover visibility gap (editor and web):** the server can fall back to another model **below the bridge** (`getFallbackChain`), and the call doesn't report the served model. So an editor or web run that failed over isn't marked in `speaker_model_failovers`, and would count as a clean replication. **Closed by #3118 (below) for desktop (with #3061) and for web (with #3111 and #3154).** Engine-path rows were always certified.

**Desktop served model (#3061, `69d46308`, t/4048, SO-confirmed e/275#29):** the desktop backend's `generateText` now returns `servedModel`. That is the registry id the call resolved to after defaulting, derived rather than echoed from the request, and set only on success. Desktop has no fallback chain, so today it always equals the requested or defaulted model. A structural tripwire test guards that exemption.

**Renderer per-turn promotion (#3118, `4647cfcc`, t/4044, SO e/281; closes t/4040):** the renderer now consumes `servedModel`, in `failoverTracking.ts`. Each speaker turn reports the requested and served model through `makeStageGenerate`:
- **served absent:** the session sets the sticky latch `failover_untracked` and stays `'unavailable'`. The latch is never cleared, so a later observed turn cannot promote it.
- **served differs from requested:** the turn is recorded in `speaker_model_failovers` for that speaker, the engine's shape, so the gate excludes the row.
- **otherwise:** the session becomes `'tracked'`, unless the latch is set.
- **on load:** a session saved before #3118 that has speaker turns, isn't `'tracked'` and has no latch gets the latch (history unknown), so resuming it can never certify turns nobody observed (SO e/281#2 condition 1).
- **zero speaker turns:** stays `'unavailable'`.

**Effect on the count:** desktop editor sessions created from #3118 onward count toward n ≥ 10, because desktop always reports `servedModel`. Desktop sessions created before #3118 stay excluded, through the latch. **Web:** the server backend emits `servedModel` (#3111, `9e6a0f67`, t/4067), and from #3154 (`dae9a5c6`, t/4125) the `/api/ai/generate` route forwards it to the renderer. Web sessions therefore earn `'tracked'` too, but only from the hosted deploy that includes `dae9a5c6`: sessions created on an earlier deploy saw no `servedModel`, latched, and stay excluded. Unlike desktop, web has a real fallback chain (`aiBackends.ts`); a turn answered by a later link reports that link's registry id, so it is recorded as a failover and the run is excluded. The paid-key fallback changes only the key, not the model. Search-grounded calls carry no `servedModel`, but speaker turns never use search. Only speaker turns are tracked, matching the engine; moderator, synthesis and evaluator calls are not covered.

**Stage models in the key (t/4098; engine #3161, `b880ce35`, t/4127; editor #3177, `3b503836`, t/4128):** speaker turns also run through per-stage models (brief, plan, draft, cite and others). Runs that differ only in those used to pool as replications. They are model identity, not config, so they go into the 4th key segment, the model fingerprint, rather than a new segment; that keeps the CL ruling at t/1668#2.
- **Override suffix:** when a run has explicit stage overrides, the fingerprint (`model_api_id`, or `model_pool` for multi-provider runs) gains `;st=` plus the overridden stages, sorted by name, each written as `stage=registryId:apiModelId`. The input is the overrides **as configured**, not the resolved session `stage_models`: the engine always records all nine stages and cannot tell an override from a default. An override equal to the default still adds the suffix; that can only over-split, never wrongly pool. Empty dialog entries are dropped.
- **Stage-default token, editor only:** with no overrides, the engine runs every stage on the debate model, but the editor runs the brief stage on the speaker's own model. Rows from both paths share `prompt_version` and can share a key, so editor **multi-provider** fingerprints end with `;sd=speaker`. Single-model runs need none, because the two defaults coincide there. The engine adds no token.
- **The editor computes its suffix by calling the engine's own `computeModelFingerprint`,** so the two paths match by construction.
- **Effect on the count:** runs without stage overrides keep byte-identical keys, single-model or engine. No calibration epoch starts for them. Runs with overrides form their own groups. Editor multi-provider runs split from engine multi-provider runs, and that history is short, since editor tracking began with #3118. Today 12 of 302 saved sessions record stage models, in 4 combinations (evidence at t/4098).
- **Provenance:** stipulated (a design decision recorded at t/4098#1 and #2, not derived from data).

**behaviour_revision, the 5th key segment (t/4145, t/4166; #3225, `1c5b5528`):** `PROMPT_VERSION` was never bumped between 2026-07-22 and this change, across about 70 commits to prompts, the turn pipeline and convergence logic, so every key pooled several instruments. Identity no longer depends on a human remembering to bump a constant.
- **The value:** the first 12 hex chars of a sha256 over a **declared** set of behaviour-bearing files (`lib/debate/calibrationLogger/behaviourRevisionFiles.ts`, data reviewed by CL). The set: `lib/debate/prompts/`, `lib/debate/turnPipeline/`, `convergenceSignals.ts`, `phaseTransitions.ts`, `cruxResolution.ts`, `debateEngine/modelResolution.ts`, and the editor's `useDebateStore/shared/modelConfig.ts`. Sources are normalized (comments stripped, whitespace collapsed), so comment and formatting edits don't start an epoch.
- **Generated at build time** (`behaviourRevision.generated.ts`), because the hosted server has no source files. A CI test fails if the committed value is stale, including when only the editor file changes.
- **Key:** `fixedConfigKey` = config_revision | prompt_version | model | model fingerprint | behaviour_revision. It is a provenance segment, so the t/1668#2 rule against widening the key with config knobs is untouched. Rows without it pool in the legacy group (empty segment).
- **Effect on the count:** keys now move whenever a declared file's behaviour changes; at the observed rate, about every 3 days. n ≥ 10 will be reached rarely. That is the honest state of the evidence, because there's no replication across an instrument that keeps changing. Regression reads work within short windows, or on a deliberate code-stable replication batch.
- **Known gaps:**
  - The regex comment-stripping also strips `//` inside strings. `prompts/moderator.ts` has model-facing `// REQUIRED when intervene=true` instructions inside a prompt template, so edits to them don't move the key (fix: a real tokenizer, t/4205).
  - Behaviour-bearing code outside the declared set: the set must grow as modules move.
  - A provider changing the model behind an unchanged id (t/4174) moves no key; t/4195 is the detection path.
- **Provenance:** stipulated (design at t/4145#1, accepted at t/4166#2).

**What `'tracked'` means:** *failover-tracked*, not *provider-identity-verified*. It says which registry model the call was routed to, not that the provider served that model. `providerReportedModel` is deliberately not read, which keeps its forensics exemption. Provider identity remains the separate e/257 check (the ai.model_identity flight-recorder event). `failover_untracked` is an internal latch: only the debate store reads it, and the gate reads `failover_tracking` alone (exemption with lapse condition recorded at the field in `lib/debate/types/session.ts`).

**`failover_tracking` (SO e/268#6, CL e/268#10):** each fingerprinted row states whether its writer could see failover. The engine writes `'tracked'`. Editor and web sessions start `'unavailable'` and earn `'tracked'` per turn (#3118, above): desktop from `4647cfcc`, web from the hosted deploy that includes `dae9a5c6`. **The gate counts a fingerprinted row only when it says `'tracked'`.** A fingerprinted row without the field is excluded with a WARN, because "tracked" must be an explicit claim and never the default. **An explicit `'unavailable'` excludes the row whether or not it is fingerprinted** (checked before the fingerprint branch; SO e/268#23). It covers the editor's not-loaded-registry fallback, which stamps no fingerprint (t/4044). Legacy rows (no fingerprint, no field) stay in the model-mixed group and count as before. Provenance class: instrument provenance, and semantic, because the gate branches on it.

## 18. Citation-link leg-a coverage floor (t/4042, SO e/266#10)

Leg-a of the data repo's citation-link check (`Test-CitationLinkIntegrity`, summary-to-node link resolution) is a **failing check** as of data PR #29. A leg-a that examined nothing would report `pass=True offenders=0`. To stop that, the leg-a result reports how much it checked (#3007, `5c33bd7b`), and `ai-triad-data/.github/workflows/citation-link-integrity.yml` fails closed when either count is absent or below the floor. **These are corpus-integrity thresholds, not `CalibrationDataPoint` fields, so they're excluded from the §5 count.**

| Threshold | Value | Provenance | Evidence / notes |
|---|---|---|---|
| `summariesScanned` floor (summary files read by leg-a) | ≥ 400 | **stipulated** | 50% of 870 summaries on data `02c0c2c9` (2026-10-07). Three counts agree exactly: PowerShell #3007, DevOps, and CL via `git show origin/main:`. Clean-data run 37566351376 reported `summariesScanned=870`. |
| `refsChecked` floor (non-blank refs passed to `Resolve-Ref`) | ≥ 8000 | **stipulated** | 50% of 16,676 refs: 11,424 `key_points[].taxonomy_node_id` and 5,252 `factual_claims[].linked_taxonomy_nodes[]`. Blank and null refs aren't counted. (CL's first count of 16,685 included 9 blank links; t/4042#8.) |

**Why 50%:** the floor targets an emptied or narrowed scan, such as a moved directory, a bad checkout path or a sparse checkout. Those drop the counts to roughly zero, far below the floor. Normal corpus change is growth, and summaries are rarely removed, so 50% leaves wide headroom for genuine removals. It isn't fitted to any distribution, so it's stipulated.

**Proven arms (data #29 final head `86450101`, t/4042#11):** an empty summaries directory goes RED with "leg-a evaluated below floor (summariesScanned=0 / 400, refsChecked=0 / 8000)" (run 37567172256). A missing leg-a goes RED with "not evaluated" (run 37566900155). The `lega=pass` output is written only after both guards pass, so a below-floor run can't auto-close an open leg-a issue as recovered.

**Revisit when** the corpus shrinks by design (for example, a summary purge or a split into a second repo). Then reset the floor against the new count in the same change.
